# Key Decisions

## 1. 역할 범위는 협업형 MDR로 정확히 설명한다

최종 정오탐 판정과 Endpoint·Full Disk 1차 대응을 전부 직접 수행했다고 말하지 않는다. SK쉴더스가 1차 분석·대응을 담당했고, 본인은 Custom 이벤트와 반복 Alert를 Event Search로 재검증해 오탐 사유·정상 운영 근거·보고서 내용을 만들었다고 설명한다.

이렇게 해야 실제 업무 분장을 지키면서도 로그 기반 검증, 고객 커뮤니케이션, 운영 개선 역량을 보여줄 수 있다.

## 2. Alert의 상태와 기술적 판정을 구분한다

`Resolved`는 운영 workflow 상태이고 `False Positive`는 분석 판단이다. 따라서 쉴더스가 Resolve 처리한 이벤트를 모두 기술적으로 오탐이라고 단정하지 않는다. 보고서 작성 전 Event Search에서 정상 프로세스·파일·네트워크 흐름을 확인한 근거를 별도로 남긴다.

## 3. 예외처리는 최소 범위로 설계한다

ANAGENT는 정상 자동화 작업이라는 이유만으로 프로세스 전체나 서버 전체를 허용하지 않는다. `anagent` 태그와 승인된 파일 해시가 동시에 일치하는 경우로 범위를 제한한다. 태그는 자산 분류 조건이지 태그만으로 모든 탐지를 해제하는 근거가 아니다.

## 4. 예외와 탐지를 함께 설계한다

정상 자동화 IP는 허용하되, 예외 대상 Agent의 22222 포트로 허용 목록 밖 Source IP가 접근하면 탐지하는 STAR Custom Rule을 추가한다. 예외로 줄어든 Alert와 별도 Rule로 보완한 보안 통제를 함께 설명한다.

## 5. 탐지 테스트에서는 미탐과 미승격을 구분한다

명령어 실행 로그가 수집됐는지, Behavioral Indicator가 생성됐는지, 최종 Threat Alert로 승격됐는지를 분리해 확인한다. “명령어를 실행했는데 Alert가 없었다”는 사실만으로 로그 수집 실패나 제품 장애라고 결론 내리지 않는다.

## 6. 수치와 비교 기준을 함께 제시한다

ANAGENT 수치는 동일한 7일을 적용 전후 비교한 결과로 표현한다. 주요 `sshd`·`sftp-server` 탐지가 1,094건에서 663건으로 431건, 약 39.4% 감소했다는 기준을 유지한다. 다른 집계 범위의 수치는 원본 증적과 범위를 확인하기 전에는 섞지 않는다.
